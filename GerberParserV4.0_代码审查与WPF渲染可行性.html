GerberParserSmartV4.0 代码审查报告

审查对象：D:\MyWork\Gerber\选点软件\高清版V4\GerberParserV4.0　·　 WinForms / .NET Framework 4.8 / HALCON 19.11　·　2026-09-17

结论速览

  1. 这个软件的渲染层结构性地走错了路。每次重绘都重新生成全部图形对象（GEN + CONCAT 共约 3 万次 HALCON 算子调用），而正确的做法是几何只建一次、交互只改变换。当前铜层图形量 15,359 个，单帧实测量级在 140–490 ms，这就是拖拽卡顿、以及"必须刷两次才显示"的根源。
  2. 点选一次要跑 2,960 万次比较。GetAllCirclesFromApertures() 在每次鼠标点击时重建 15,359 个对象，并在循环内对 3,852 个已选点做线性查找，选中点越多越卡。
  3. HALCON 在这个工程里只被用来画图。全部算子调用只有 GEN_* / ConcatObj / DispObj / SetColor，没有任何图像处理算法；数据源是 GerberParserTool 的纯坐标（List<ValueTuple<double,double>>）。为画图背一个 19.11 运行时 + license 授权，代价与收益严重不匹配。
  4. 原生 WPF 可以完全等效，且在交互场景下反超。矩形/圆/旋转椭圆都是 WPF 的一等图元，用合并 StreamGeometry + RenderTransform 的正确姿势，拖拽平移缩放时几何零重建、走 GPU 变换，与当前实现相差一个数量级以上。
  5. 另有 12 项正确性/健壮性缺陷和 7 项工程构建问题，其中「缩小到一定程度绘制中断」「右键退出选点模式未实现」「锁定按钮文案反了」「Console 日志在 WinExe 下全部丢失」四项会直接影响使用。

二、缺陷清单

A 级 · 渲染与交互性能（架构性问题）

A1每帧全量重建几何 —— 所有卡顿的总根源

MainForm.cs:179-207（Paint）、253-306（DrawAllTemplateCircles）、363-445（DrawGerberApertures）

现状：hWindowControl1_Paint 每次都执行 ClearWindow()，然后遍历全部图形逐个 GenCircle / GenRectangle1 / GenEllipse，逐个 ConcatObj 拼接，最后 DispObj。

量级：铜层 15,359 个图形 ⇒ 每帧 15,359 次 GEN + 15,359 次 ConcatObj + 98 次 DispObj，约 3.1 万次跨托管/非托管边界的算子调用。每次算子调用包含参数编组、错误码检查、异常路径构造，典型开销 3–20 µs，单帧合计 约 140–490 ms。

触发频率：拖拽（HMouseMove → RefreshHalconWindow，MainForm.cs:791）每移动一次触发一帧；滚轮每格一帧；此外任何 WM_PAINT（窗口被遮挡后恢复、最小化还原、其它窗口从上方移过）都会触发。

附带问题：循环里的 ConcatObj(acc, single, out acc) 是累积拼接，每次都要重建整个对象元组，条目拷贝总量呈 O(n²)（n=15,359 时约 1.2 亿次条目复制）。

修复方向（收益递增）：

  • ① 把每层的 HObject 缓存到字段，只在数据变化时重建，一次重建可复用 N 帧。
  • ② 用 SetPart 做缩放平移：几何保持世界坐标，SetPart(row1,col1,row2,col2) 定义视口，HALCON 会按当前 part 变换并光栅化。拖拽缩放时几何完全不用重建。
  • ③ 批量构造对象元组：先把单个 HObject 收集进 List，避免在循环里累积 Concat。
  • ④ 可考察 SetWindowParam 的 backbuffer（19.11 支持情况需实测确认），让静态层内容缓存在后台缓冲。
  • ⑤ 换掉 HWindowControl 用 WPF（见第四节）。

A2每次点击重建全部图形 + 线性查找，O(N×M)

MainForm.cs:828-887（HMouseDown）→ 1003-1047（GetAllCirclesFromApertures）→ 1049-1088（GetShapesByPos）

现状：每次左键点击都调用 GetAllCirclesFromApertures()，对 15,359 个位置逐个调用 _selectedCircles.FirstOrDefault(c => c.X == position.Item1 && c.Y == position.Item2 && ...)，即在外层循环内做一次 O(M) 线性查找。

量级：15,359 × 平均 1,926 次比较 ≈ 2,960 万次带闭包的委托调用 + double 比较，估计 0.2–1 s/次点击。已选点越多越慢，是典型的"越用越卡"。

修复：解析完成后一次性构建全量实体列表，用引用维护选中状态；命中查找改用均匀网格哈希（cell 边长取最大光圈直径），把 O(N) 降到 O(1)。

A3多选模式：同 ID 全量扫描 + 嵌套线性判重

MainForm.cs:927-956（HandleMultipleSelect）→ 958-988（IsSingleShapeInShapes）

现状：先 allShapes.Where(c => c.ID == clickedShape.ID)（O(N)），再对该光圈下每个形状调用 IsSingleShapeInShapes(shape, _selectedCircles)（O(M)）。代价 O(N + K×M)，K 为同 ID 位置数。

风险：焊盘阵列常常几百上千个同 ID 位置，K=1,000、M=3,852 时是 385 万次比较，叠加 A2 后是卡顿主因之一。

修复：ID → 索引列表的字典；选中集合改用 HashSet<SelectedCircle>（引用语义）。当前用 List.Remove/Contains，既线性又依赖引用相等，一旦对象实例被重建就会静默失效（表现为"选不中 / 重复添加"）。

A4翻转开启后 O(N²) 的包围盒重算

MainForm.cs:1856-1877（ApplyMirrorTransform）、888-909（ReverseMirrorTransform）、1880-1901（ApplyMirrorTransformToRect）

现状：三个方法内部都调用 ViewportHelper.CalculateBoundingBox(_apertures)，该函数遍历全部光圈的全部位置。而 ApplyMirrorTransform 在 DrawGerberApertures 的每个位置循环里被调用一次。

量级：15,359 次 × 每次遍历 15,359 个位置 = 2.36 亿次迭代/帧。

边界：未翻转时方法提前 return，不会触发 —— 所以缺陷表现是"平时能忍，一点翻转立刻卡死"，容易被误判成别的原因。

修复：包围盒与中心点在解析/加载后算一次并缓存；或改成关于画布中心翻转（只需窗口尺寸，零成本）。

A5选中层被重复绘制两次，且选中/未选中颜色完全相同

MainForm.cs:210-235（DrawTemplateMode）、253-306、309-361

现状：DrawTemplateMode 先无条件调用 DrawAllTemplateCircles() 画出全部 _selectedCircles，随后又在 _isSelectingMode && 有 IsSelected 时调用 DrawSelectedCircles() 把其中已选中的再画一遍。

问题 ①（性能）：两个方法都用同一个 _selectColor + SetDraw("fill")，最终像素完全一致 —— 第二次纯属重复劳动。模板加载后所有形状 IsSelected=true，于是 3,852 个形状被画两遍，每帧多出 3,852 次 GEN + 3,852 次 ConcatObj。

问题 ②（功能）：既然两层用同色同风格，视觉上根本无法区分"已选中"与"未选中"。参数设置里的"选中颜色"配置（ParamsForm）也就没有实际意义。这多半不是设计意图，而是重构中途的遗留。

修复：明确两层语义（例如未选中=空心描边，已选中=实心填充 + 高亮色），只在状态变化时重建选点层。

A6Invalidate + Update 双刷新，"必须刷两次才显示"

MainForm.cs:744-761（RefreshHalconWindow，注释在 748 行）

//必须要刷新两次才能正确显示
if (hWindowControl1.Visible && hWindowControl1.Width > 0 && hWindowControl1.Height > 0)
{
    hWindowControl1.Invalidate();
    hWindowControl1.Update();
}

机理：Invalidate() 只标记无效区，Update() 强制同步处理 WM_PAINT。在 HWindowControl 这种自己处理 WM_PAINT 的子窗口上，Update() 期间的重绘会与系统随后派发的 WM_PAINT 交错；因为单帧绘制本身要花上百毫秒，第一次的结果被系统擦除，于是"第二次才可见"。被注释掉的重复块说明当时是靠再刷一次绕过去的。

本质：这是"绘制太慢 + 非双缓冲"的症状，不是刷新次数的玄学。修掉 A1 之后这个注释就可以删了。

交互层建议：拖拽这类高频路径应做节流 —— 只 Invalidate() 交给系统节拍，或用 16 ms 定时器合并重绘请求。

B 级 · 正确性与健壮性

B1缩放到一定程度后，绘制会中断（GEN 半径低于 HALCON 下限）

MainForm.cs:275-277、331-332、412-413（radius 计算）；49（_halconScale 初值）；660-699（ResetHalconViewToCenter）

机理：绘制半径写的是 windowR = (Diameter / 2) * _halconScale。HALCON 的 gen_circle / gen_ellipse 要求半径 ≥ 0.5 像素（控制参数下限）。缩放到 scale < 0.5 / (Diameter/2) 时，半径会低于下限。

后果链：算子抛 HOperatorException → 被 hWindowControl1_Paint 的 catch (Exception ex) { Console.WriteLine(...) }（203-206）静默吞掉 → 而 ClearWindow() 已经执行过 → 用户看到黑屏或只画了一半的残缺画面。

确认方法（本地 3 行）：

// 在 foreach 之前插入，观察是否走到这里就断掉
double windowR = (shape.Diameter / 2) * _halconScale;
System.Diagnostics.Debug.WriteLine($"r={windowR:F4} scale={_halconScale:F4}");
if (windowR < 0.5) { /* 计数并跳过 */ continue; }

修复：windowR = Math.Max(windowR, 0.5)，或按 LOD 直接跳过亚像素图形（缩小到该级别时它们本来也看不出来）。

B2scale 可能为 0，导致除零 / NaN 传播

MainForm.cs:49（初值 0.00）、662-663（提前 return）、849-850（除法）

触发路径：加载模板时目录里没有 Gerber 底图 → _apertures = new List<Aperture>()（1595 行）→ ResetHalconViewToCenter() 在 662 行直接 return，_halconScale 保持 0 → 之后点击选点：actualX = (e.X - _halconOffsetX) / _halconScale = ±∞ 或 NaN。

表现：NaN 参与的所有比较都是 false，点击没有任何反应（看似"点不动"）；绘制半径算出来是 0 或 NaN，画面空洞。

修复：无数据时把 scale 设为 1、offset 设为 0；除法前加 Math.Abs(_halconScale) < 1e-9 保护。

B3提示语承诺的"右键退出选点模式"根本没有实现

MainForm.cs:1090-1099（StartSelectingMode 的 MessageBox）、766-776（HMouseUp）、828-887（HMouseDown）

状态栏（1095）和弹窗（1097）都写着"右键退出选点模式"，但 HMouseDown 只处理 Middle（拖拽）和 Left（选点），HMouseUp 只处理 Middle。右键分支完全不存在，用户按提示操作没有任何效果，只能去点按钮。

修复：在 HMouseDown 补 if (e.Button == MouseButtons.Right) { _isSelectingMode = false; ... }，或改掉提示文案。

B4锁定按钮的状态与文案是反的

MainForm.cs:578-593（btnLockAll_Click）

if (_isSelectingMode)
{
    _isSelectingMode = false;
    btnLockAll.Text = "取消锁定";   // 已经退出了，却显示"取消锁定"
}
else
{

两个分支的文案赋值互换了。用户看到"锁定"时其实已经在选点模式，看到"取消锁定"时其实已经退出，加上 A5 的选中色不区分，整套锁定/解锁的交互反馈是失真的。

B5框选判定用"圆心在框内"，而非"图形与框相交"

MainForm.cs:1191-1199（GetCirclesInSelectedRegion）、对比 1049-1088（GetShapesByPos）

点选用"点落在图形内"，框选却用"圆心落在矩形内"，两个语义不一致。视觉上明显压在框里的图形，只要圆心在框外就会被漏掉，用户会认为框选漏点。

修复：改成圆与矩形相交判定（圆心到矩形最近点距离 ≤ 半径），矩形/椭圆同理按其外接几何求交。

B6区域选取异常路径不恢复按钮状态

MainForm.cs:1110-1188（StartRegionSelectingMode）

进入时把 btnSelectRegion.Enabled = false、背景改灰（1121-1122），放在 BeginInvoke 里。若 DrawRectangle1 抛异常（1183-1186），catch 只打日志，没有恢复 Enabled 和 BackColor → 按钮永久变灰，用户再也框选不了，只能重启。

另外，HOperatorSet.DrawRectangle1 是阻塞式交互算子，内部自建消息泵等待用户画框。在 UI 线程上跑它会让整个窗口（包括所有按钮）在这期间失去响应，这是设计层面的妥协，WPF 方案里可以用纯托管鼠标事件替代。

B7pressAltKey() 是散落各处的创可贴

MainForm.cs:733-738（定义）、655、696、1096、1143、1216（调用）

用 keybd_event 模拟 Alt 按下+抬起，出现在提取坐标、重置视图、进入选点、框选、以及 ProcessCmdKey 中。系统级注入按键的副作用：Alt 会激活窗口菜单栏并可能抢占焦点；ProcessCmdKey 里每按一个键就发一次 Alt（1216 行在 switch 之前无条件调用），这是最不该出现的位置。

判断：这多半是早期为解决 HALCON 窗口的焦点/键盘消息问题而加的通用补丁，根因从未定位。不要直接删，先用注释法逐个排除（每次只注解一处，验证对应功能），确认哪一处是真正必要的，再针对性用 SetFocus / SetWindowParam('flush') 或正确的消息处理替代。

B8所有诊断日志都是死代码

全工程 20+ 处 catch { Console.WriteLine(...) }，如 205、714、759、885、1185 等；csproj:8 OutputType=WinExe

OutputType 是 WinExe，没有控制台，Console.WriteLine 的输出全部丢弃 —— 包括 _parser.PrintSummary() 的解析统计（MainForm.cs:640）和所有绘制异常信息。线上出问题时零线索，这也是 B1 的黑屏现象难以自查的原因。

修复：换成写文件的日志（或 Debug.WriteLine + TraceListener 指向文件），并把 catch 里的空日志升级为"记录完整堆栈"。

B9无 DPI 感知声明 + HALCON 窗口尺寸不同步

App.config（无 dpiAware）；MainForm.Designer.cs:405-406（AutoScaleMode=Dpi，基准 96）；163-166（构造时一次性设置）；Designer.cs:388（WindowSize 硬编码 956×928）

进程没有声明 DPI 感知，在 125%/150% 缩放的显示器上，整个窗口被 DWM 位图拉伸 —— 对一个自称"高清版"的工具是直接打脸：文字和 Gerber 图形都会发虚。

更麻烦的是 HALCON 侧：构造时用控件当时的尺寸调了 SetSystem("tsp_width/height") 和 SetPart（163-166），之后再没有同步。Form 无 Resize 处理，且 hWindowControl1.WindowSize 被硬编码成 956×928。窗口最大化后，SetHalconViewport() 里用的 hWindowControl1.Width 是逻辑值，与 HALCON 窗口的物理像素尺寸不一致 → 显示区域只占控件一部分。

修复：加 PerMonitorV2 的 DPI 感知 manifest；在 Resize/SizeChanged 里重建 HALCON 窗口尺寸并重算视口。

B10覆盖保存不是原子操作，存在半破坏窗口

MainForm.cs:1372-1375（先 Delete）、1476-1477（后 WriteAllText）

if (File.Exists(jsonFilePath)) { File.Delete(jsonFilePath); }   // 先删
...

两步之间若崩溃/断电/磁盘满，模板只剩 Gerber 底图、JSON 丢失，而原数据已不可恢复。修复：写临时文件后用 File.Replace 原子替换。

另：SaveTemplateFile（1243-1294）的"同名覆盖/异名新建"分支与 SaveTemplateToPath（1352-1383）内部的"文件夹已存在，是否覆盖"询问会叠加，用户可能被连问两次而点错，覆盖掉别人的模板。

B11JSON 用 dynamic 解析，弱类型且无校验

MainForm.cs:1637-1727（LoadJsonFormat）、1544（dynamic jsonData = DeserializeObject(...)）

全流程走 DLR 动态绑定，没有编译期检查，字段拼错要到运行时才炸且异常信息难以定位。而 131-146 行已经定义好的强类型 TemplateData / MirrorState 类完全没有被使用——正是为强类型反序列化准备的死代码。

建议：直接用 JsonConvert.DeserializeObject<TemplateData>(...)，配 JSchema 或手写字段校验，加载失败时给出"哪个字段不对"的明确提示。

B12共享 _parser 单例 + 全局静态 Program.FileName

MainForm.cs:38、639-641、1589-1590；Program.cs:14

同一个 GerberParser 实例被反复 ParseFile，每次用 _apertures = _parser.GetApertureList() 直接替换字段引用；输入路径通过全局静态字段 Program.FileName 传递（默认值还是写死的绝对路径）。每次解析是否彻底清理上一次的状态，取决于 GerberParserTool 内部是否调用了它的 Reset()（无法从工程内确认）。建议在 ParseFile 前后各做一次数据量断言（光圈数与位置总数），一旦异常增长就是状态泄漏。

C 级 · 工程与构建

C1引用指向自身输出目录（跨配置版本漂移）

csproj:56-62

<Reference Include="GerberParserTool" ...>
  <HintPath>bin\Debug\GerberParserTool.dll</HintPath>    <!-- 输出目录当输入库 -->
<Reference Include="halcondotnet">
  <HintPath>bin\x64\halcondotnet.dll</HintPath>

Debug|AnyCPU 输出到 bin\Debug\，而 x64 配置输出到 bin\x64\Debug\。x64 配置构建时，GerberParserTool 仍从 bin\Debug\ 取上一个配置的产物，两个配置会互相覆盖/链接到旧版本。应把第三方 dll 移到固定的 lib\ 目录或改为项目引用。

C2Release|x64 里的 Prefer32Bit=true 自相矛盾

csproj:53（Release|x64 段内）

Prefer32Bit 只对 AnyCPU 有意义，x64 平台下该设置是错误配置（无害但会误导）。更实际的风险是架构匹配：halcondotnet.dll 是 MSIL（AnyCPU），真正决定架构的是机器上的原生 HALCON 库；bin 里不含原生库，一旦 32/64 位不匹配，会以 BadImageFormatException 或"找不到模块"的形式爆出，且异常信息不友好。

推算依据（讲讲为什么差这么多）：

  • HALCON 的窗口绘制是立即模式：每次重绘都要"重放全部对象 + 重新光栅化"。region 内部是游程编码（RLE），光栅化本身很快，但 3 万次算子调用的固定开销逃不掉。
  • WPF 是保留模式：几何 → 三角形 → 顶点缓冲，一次性上传 GPU 后缓存；之后每帧只提交变换矩阵，光栅化由 GPU 完成。956×928 视口全屏填充约 0.9 M 像素，即便 4× 多重采样也只有 3.5 M 采样点，对现代 GPU 是毫秒级的事。
  • 所以差距不是"调优"能弥合的，它来自渲染模型本身。HALCON 缓存化后也能达到与 WPF 同量级的可用水平，WPF 的优势主要体现在图形量继续增大时（比如换成整板 Gerber 或加多层叠加）仍然稳定。

四、原生 WPF 能否等效？性能是否等价甚至反超？

4.1 结论

能等效，且在"拖拽 / 缩放 / 大量图形"这个场景下反超；静态首帧成本两者相当。
矩形（DrawRectangle）、圆（DrawEllipse / EllipseGeometry）、旋转椭圆（PushTransform + DrawEllipse）都是 WPF 的一等矢量图元，表达力上不存在"画不出来"的问题。真正的差距在渲染模型，见上节。

4.2 等效实现的关键点（用错姿势会比现在还慢）

  1. 一个 DrawingVisual 承载一层，几何合并进一个 StreamGeometry。绝对不要"每个图形一个 Shape/Ellipse 控件"—— 那会带来 15,359 个 UIElement 的布局、命中测试和渲染开销，帧率会掉到个位数并且内存暴涨。
  2. 构建后 Freeze()。StreamGeometry、Brush、Pen 全部冻结，WPF 才能缓存 GPU 侧资源、并允许跨线程使用。
  3. 缩放平移只改 RenderTransform（MatrixTransform），绝不重建几何。这是与当前实现最本质的区别：_halconScale/_halconOffsetX/Y 这套"手工变换 + 重建几何"的整体思路被一个矩阵取代。
  4. 分层：底图 / 选点 / 交互三个独立 Visual。换文件才重建底图；选点状态变化才重建选点层；拖图时两层都不动，只改矩阵。
  5. 命中测试用自建均匀网格哈希（cell 边长取最大光圈直径），点选 O(1)。不要用 VisualTreeHelper.HitTest 遍历，也不要用 List.FirstOrDefault。
  6. 数据源不需要经过 HALCON。Aperture.Position 就是 List<ValueTuple<double,double>>，直接用来生成几何即可。

4.3 反超的机理（讲清"为什么"）

  • 当前实现的瓶颈是 CPU + 互操作：3 万次调用 × 每次几微秒，与图形数量线性相关，且缩放平移时反复重跑。
  • WPF 方案的瓶颈是 GPU 填充率：与"视口像素面积"相关，与"图形总数"几乎无关（屏幕外的三角形被裁剪掉）。你的视口固定 956×928，所以这个上界是恒定的小数。
  • 这就是"反超"的来源：当图形数量增长时，当前实现线性恶化，WPF 几乎不变。你现在 15,359 个图形已经卡到必须刷两次；如果哪天要加载整板、叠加多层，差距会变成碾压式的。

4.4 风险与边界（什么情况下 WPF 反而更差）

  1. 没有硬件加速时会塌方。远程桌面、虚拟机、无显卡驱动的环境下 WPF 会回退到软件渲染，此时它比 HALCON 的 GDI 路径慢得多。如果这个工具要跑在工控机的远程会话里，必须先在这类环境实测，这是最大的风险点。
  2. 极致放大需要 LOD 配合，否则圆会多边形化（见上表）。
  3. 如果你后续要用 HALCON 做图像处理（模板匹配、Blob、测距），那 HALCON 的 region 是必须保留的中间表示。但就本工程现状看，当前一个图像处理算子都没用，纯画图。
  4. 首次渲染的三角化是单线程 CPU 成本（milcore），15,359 个描边圆可能几百毫秒。用加载提示遮一下即可，且只在换文件时发生一次。

4.5 顺带的两个收益（可能比性能更重要）

① 消除 halcondotnet 19.11 的授权与部署负担。你在 RBLAOI 项目里正是因为 halcondotnet 19.11 不允许商业化而做了去 Halcon 化；这个工程又引入同一版本，而且用得比那边更"奢侈"——纯画图。改用 WPF 渲染后：csproj 去掉 halcondotnet 引用（csproj:60-62）、删掉 PublicMethod.SetHalconViewport、不再需要目标机器安装 HALCON 19.11 运行时与授权。分发一个 exe 就能跑。

② 改动面很小。解析层 GerberParserTool 是纯 .NET、与 HALCON 无耦合，原样保留。要改的只有渲染与交互层：MainForm 的绘制区（约 400 行，含 #region Halcon绘制优化版本 整块）和鼠标事件，加上 csproj 的一处引用。
