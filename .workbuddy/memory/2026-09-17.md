## GerberParserSmartV4.0 代码审查 + WPF 渲染可行性分析

产出：`GerberParserV4.0_代码审查与WPF渲染可行性.html`（工程根目录）

### 工程实况（实测）
- WinForms / net48，`HalconDotNet.HWindowControl` 956×928（Designer.cs:379-388）
- halcondotnet **19.11.0.0**（MSIL）；bin 内**无** native HALCON 库 → 运行时依赖机器已装 19.11 + 授权
- 铜层样例 1516601-00-C_01.GBL：19,774 行，D03=1,520 / D01=13,839 → **约 15,359 个图形**，98 个光圈
- 已用模板最大规模：`bin\x64\Debug\Json\MAX!\circles.json` = **3,852 个选中形状**
- `Aperture.Position` 是 `List<ValueTuple<double,double>>`（值类型，无额外堆对象）
- GerberParserTool.dll 是纯 .NET，与 HALCON 无耦合 → 可原样保留

### 核心结论
1. 渲染层走的是"立即模式 + 每帧全量重建几何"：每帧约 3.1 万次 HALCON 算子调用 → 推算 140–490 ms/帧。
   正确做法是几何建一次 + 用 SetPart 做视口变换。这是"必须刷两次才显示"的根源。
2. 点选一次成本 O(N×M)：`GetAllCirclesFromApertures()`（MainForm.cs:1003）对 15,359 个位置逐个做
   `_selectedCircles.FirstOrDefault(...)`（3,852 元素线性查找）≈ 2,960 万次比较/点击。
3. 翻转开启后 `ApplyMirrorTransform`（1856）在每个位置循环里调 `CalculateBoundingBox` → O(N²)=2.36 亿次/帧。
   未翻转时提前 return，所以表现为"一点翻转就卡死"。
4. 新发现缺陷：缩放到 scale < 0.5/(Diameter/2) 时 GEN 半径低于 HALCON 的 0.5px 下限 → 抛异常被
   Paint 的 catch 吞掉（ClearWindow 已执行）→ 黑屏/残缺画面。待本地实测确认。
5. 确认的功能性 bug：右键退出选点模式未实现（提示语却写了）；btnLockAll 文案与状态反了（578-593）；
   框选用圆心而非相交；区域选取异常不恢复按钮 Enabled → 永久变灰。
6. 全部 `Console.WriteLine` 诊断在 WinExe 下丢失（无控制台）→ 修 B8（日志落地）应排第一优先级。
7. 工程构建：csproj HintPath 指向自身输出目录（bin\Debug / bin\x64），跨配置版本漂移；
   Release|x64 里 Prefer32Bit=true 矛盾；App.config 无 DPI 感知声明（"高清版"却会发虚）。

### WPF 结论
- 等效可行（矩形/圆/旋转椭圆都是一等图元），交互场景**反超**：拖拽缩放几何零重建、走 GPU 变换。
- 正确姿势：三层 DrawingVisual（底图/选点/交互）+ 合并 StreamGeometry + Freeze + RenderTransform，
  命中测试用网格哈希；**绝不能**每个图形一个 Shape 控件。
- 四个语义差异：线宽（HALCON 是设备像素 / WPF 是 DIP）、放大后多边形化（需 LOD）、AA、颜色。
- 最大风险：无 GPU 硬件加速（远程桌面/虚拟机）时 WPF 软件渲染会塌方 → 必须实测该类环境。
- 连带收益：去掉 halcondotnet 引用即消除 19.11 授权风险与 HALCON 运行时部署依赖（同 RBLAOI 去 Halcon 化的动因）。
- 改动面小：只动渲染与交互层（MainForm 绘制区约 400 行）+ csproj 一处引用。

### 环境备注
- 沙盒内 `Add-Type` / `Reflection.Assembly.Load*` 被安全策略拦截 → 无法实测 WPF 耗时；
  只能用 PowerShell 做文件级/元数据级取证（AssemblyName.GetAssemblyName 可用）。
- 报告已给出 V1（帧耗时埋点）/V2（ConcatObj 复杂度）/V3（WPF 对照 demo）三段本地验证代码。

## 追加：架构决策调研（"改 WinForms 还是重做 WPF"）

### 工程版图（实测）
- `D:\MyWork\Gerber\选点软件\` 下有两条并行线：
  - **高清版V4**（GerberParserV4.0，MainForm.cs 1,906 行，mtime 2025/11/21）—— 每帧按当前 scale 重建几何，放大清晰但卡
  - **稳定版V5**（GerberParserV5.0，MainForm.cs 2,427 行，mtime 2026/2/27）—— **功能最全**，已做缓存化
- V5 已实现的缓存架构：`PreGenAllObj()` → `GenGerberObj()`（按烘焙时的 `_halconScale/_halconOffset` 生成 region）
  → `_gerberObj` / `_selectH1Obj` / `_selectH2Obj` / `_selectH3Obj`；拖动/滚轮走 `SetPart`（928、1019 行）不重建几何
- V5 独有功能（WPF 版的需求基线）：插针头类型 h1/h2/h3 分组 + 各自颜色、形状合并（CreateMergedShape）、
  缓存清除、缩放比例标签（UpdateScaleLabel）、翻转（MirrorHorizontal/Vertical + Reverse*）

### V5 的严重缺陷（已确认，未修）
- **选点坐标反算与 SetPart 双状态不同步**：几何烘焙用 `_halconScale/_halconOffset`（719 行 `InitialHalconViewParams`
  初始化后再无更新），缩放平移走 `SetPart`，而左键反算（1056-1057）仍用旧值
  → **中键拖动或滚轮缩放之后，点选会命中错误的图形**，错位量正比于视口平移量
- 修法（3 行）：`actualX = ((col1 + e.X * viewW / Width) - _halconOffsetX) / _halconScale`
- `GetAllShapesFromApertures()`（1219）仍是 O(N×M) 线性查找；`GetShapesByPos`（1266）O(N) 全表扫描且椭圆忽略旋转

### 核心结论：V4/V5 是同一堵墙的两面
- region 是**栅格**（像素集合），无矢量语义：不重新栅格化 → 放大失真（V5）；每帧重新栅格化 → 卡（V4）
- 但**更根本的共同缺陷是都没有视野裁剪**：成本锁定在"全图图形总数 15,359"，而非"当前可见图形数"
  → 放大到只看得见 200 个图形时，两版都还在处理全部 15,359 个

### 目标环境约束（用户确认，2026-09-17）
1. **要交付客户 / 商用** → HALCON 授权不可接受（同 RBLAOI 去 Halcon 化的原因）
2. **目标机含 RDP 远程会话 / 虚拟机 / 老工控机** → GPU 加速不可靠
3. 本次改造落点：用户反问"为什么不直接重做"

### 技术选型结论（已推翻我第一轮的 ElementHost 混合建议）
- 事实依据（微软文档）：WPF 回退软件渲染的条件包含"跑在 RDP 上"；.NET 3.5 SP1+ 在 RDP 下
  "服务端软件光栅化 + 位图远程传输"；VM 图形模拟器异常时也回退。
  **net48 无法开启 RDP 硬件加速**（`Switch.System.Windows.Media.EnableHardwareAccelerationInRdp`
  是 .NET 8 才引入且默认 false）→ WPF 在用户目标环境里 GPU 优势失效
- **推荐：留在 WinForms，用 GDI+ 自绘渲染核**（System.Drawing 框架内置、零依赖、环境无关、RDP 友好），
  复用 V5 的业务逻辑（模板/路径/镜像/合并/插针头），只替换渲染核 + 命中测试
- 关键设计（与后端无关，必须做）：
  1. **视野裁剪 + 网格索引**（按最大光圈直径建格，查询只取与视口矩形相交的格）→ 每帧成本改由可见图形数决定
  2. **三级 LOD**：N>3000 走预渲染位图 + 平移 blit（缩放停止后重渲）；300<N≤3000 走矢量批量
     （同尺寸光圈合并为一个 GraphicsPath，一次 DrawPath）；N≤300 走矢量 + AA + 精确线宽
  3. 数据摊平：把 `Aperture.Position`（`List<ValueTuple<double,double>>`）摊成一维数组（SoA），
     按光圈分组，避免每帧遍历嵌套列表
  4. **单一变换真相源**：一个 Matrix，正算与反算必须互逆（V5 就是栽在这里）
- 工作量估算：渲染核 + LOD ≈ 1.5 天；交互/命中 ≈ 0.5 天；复用 V5 业务逻辑 ≈ 1 天 → 约 3 天
- 待确认：目标机 OS（Win7 会影响 .NET 4.8 部署与更差的 GPU 加速）
