## 设计讨论：框选区域语义 + 模板保存路径（仅讨论，未改代码）

### 一、框选区域
**现状事实**
- 区域只做一件事：把 HitTest 候选集缩到框内（MainForm.cs:771-780 `GetCirclesInSelectedRegion`），本身不选点
- **隐性耦合**：过滤后的 `candidates` 同时传给 `HandleSingleSelect` / `HandleMultipleSelect`（781-790），
  而 `HandleMultipleSelect` 是 `allShapes.Where(c => c.ID == clickedShape.ID)`（844）
  → 框了区域后，多选的"同 ID 全板全选"被静默降级为"框内同 ID 全选"
- 框外点击静默失效（781 `if (clicked == null) return;`）→ "围墙感"的真正来源
- `_actualSelectedRect` 是单个 RectangleF，只能有一个区域；重新框选会先清空（1023）
- 判定口径 `ShapeQuery.IsVisible`（ShapeQuery.cs:60-67）是**外接矩形 AABB 相交**，不是"完全包含"

**改"框选即全选"的四个必答项（我的意见）**
1. 不能替代多选模式：框选=按**位置**批量，多选=按**类型**（ID）批量，互补；改后多选应恢复全板生效
2. 性能：`IsSingleShapeInShapes`（872-902）是线性扫描 → 框选 k 个就是 **O(k·n)**。
   3852 点全板框选 ≈ 1480 万次比较 ≈ 几十~200ms 卡顿；上万点进秒级。
   修法：`SelectedCircle`（57-75）未重写 Equals/GetHashCode → 默认引用相等，
   加 `HashSet<SelectedCircle>` 做去重索引即可 O(1)，全板框选 <1ms
3. 口径：建议保留"相交"（容错好），用状态栏报数补偿（"命中 47 个，总计 312 个"）
4. 必须可撤销（Ctrl+Z 回滚本次框选），否则"框大了"= 换了个位置的痛苦；锁定态应只画框不改选

### 二、模板保存路径
**回答用户的疑问**：从桌面加载的模板，同名点保存 → **覆盖桌面那份**，参数设置路径完全不参与。
决策链（`SaveTemplateFile` 1176-1200）：
| 条件 | 落点 |
|---|---|
| 有 `_currentTemplatePath` 且文本框名 == 模板文件夹名 | 覆盖该目录（可在桌面） |
| 有归属但改名了 | `设置路径\新名`，**旧模板原地保留**（数据分叉风险） |
| 无归属（刚解析 Gerber） | `设置路径\文件夹名` |

**结论**：路径设置项**该留**，但它管的是"起点"不是"终点"——
① 新模板落点（1176-1200 的 else 分支）② 加载对话框初始目录（`LoadTemplateFile:1448`）。
建议改名「新模板默认目录」，并**在界面显示当前模板完整路径**（现在 label1 只有名字，1227）。

**发现两处待用户确认的疑似缺陷**
- A：`SaveTemplateAs`（1262）调的是 `SaveTemplateToPath`，而它明确不更新 `_currentTemplatePath`（1416/1427-1430 注释）
  → **另存到新位置后，点"保存"仍写回旧位置**
- B：就地保存也会弹"文件夹已存在，是否覆盖？"（1301-1313）→ 每次保存都在提醒"另存为"，
  加剧"怪"的感觉。建议保留弹窗但把完整路径写进文案，而非去掉确认

**未采纳的方案**：改成"永远存到固定路径"——会把从桌面加载的模板静默搬走，同名不同源更难排查

## 设计讨论：「打开Gerber文件」与「加载」是否合并（仅讨论，未改代码）

**用户提出的未来方向（重要）**：后续要加**多图层**功能 —— 一个文件夹可能不止一个 Gerber，
类似 GerberView 那样叠加显示。`groupBox4`「图层」空面板显然就是为它预留的。

### 现状事实
| | 打开Gerber文件 `btnOpenFile` | 加载 `btnOpenTemple` |
|---|---|---|
| 位置 | groupBox2「基础操作」(10,20) | groupBox1「模板文件操作」(10,20) |
| Designer | 67-77 | 118-127 |
| 对话框 | 标题"选择文件"，Filter `*.*` 无过滤 | 标题"选择模板圆圈文件"，Filter `*.json` 优先 |
| 落到 | `LoadGerberFromPath(path)` 791-805 | `LoadTemplateFromFolder(父目录)` 2071-2197 |
| `_isTemplateMode` | false | true |
| `_currentTemplatePath` | 清空 | = 该目录 |
| 选点 | `ClearAllSelection()` | 从 circles.json 恢复 |
| 保存落点 | 参数设置里的模板路径 | 当前模板文件夹（就地） |

下游收敛到同一条管线（`ParseFile` → `_apertures` → `BuildAllShapes` → `_allShapes`），
差异只有 3 个状态位。**合并的技术成本很低，下游不用动。**

### 实测数据
`bin\x64\Debug\Json\` 下 5 个模板目录，**5/5 都是 circles.json + 底图并存**，
底图扩展名不成体系：`.GBL`（GBL1 / GBL2 / New\Gerber_BottomLayer.GBL）、`.GBS`（GBS1）、`.o`（MAX!\drl.o）。
→ 「按扩展名白名单识别 Gerber」不可行；`Program.FileName` 默认值也是 `.GBS`。

### 真实存在的坑（已顺代码确认）
用「打开Gerber文件」在模板目录里点中底图 → `LoadGerberFromPath` 在 `ExtractPosition()` **之前**
就无条件执行 `ClearAllSelection()`(796) / `_currentTemplatePath=""`(799) / `txtOutputFile=""`(798) /
`_actualSelectedRect=Empty`(797)，解析成功后换图 → **选点全没了**。
若改点 `circles.json`：`ParseFile` 抛异常被 `ExtractPosition` 的 catch 接住(950-953)，
但**状态清空在 try 之外**，留下"旧图 + 选点已清 + 归属已清"的半失败态。
磁盘安全：`txtOutputFile` 空 → `SaveTemplateFile` 1735 行拦下提示"请输入文件夹名称"；
`_currentTemplatePath` 空 → 不会写回模板目录。
→ **定性：损失的是重复劳动 + 一个莫名错误框，不是数据损坏。**

### 用户补出多图层方向后的结论修正
**不该现在合并。** 多图层会让两个入口的**输入粒度**分叉：
「打开模板」输入是一个目录；「打开 Gerber」输入是一批图层文件 → 合并后一个按钮要同时接受
单文件 / 多选 / 目录，判别逻辑从"猜类型"升级为"猜类型 + 猜粒度"，猜错更贵。

**但有一条跨版本有效、现在就该做**：
用「所在目录里有 circles.json」作判据 —— 多图层下依然成立且价值更大（模板目录里一堆 .gbl/.gbs，更易误入）。
用法是**拦截提示**而非自动路由：选中文件所在目录存在 circles.json 时问一句
"这看起来是模板目录，是否改为加载模板？"

### 多图层真正的坎在数据模型（不在按钮）—— 三个改造点
1. `LoadTemplateFromFolder` 挑底图（2114-2142）现在是**单选**：先 `*.gbr` → 再 `*.ger` → 都没有就
   排除 `circles.json`/`.dat` 取最近修改，且优先匹配与文件夹同名的。多图层要改成"扫出全部图层"，
   返回值从 `gerberFilePath` 变成集合，`_templateGerberFilePath`(2157) 同步改。
2. `_apertures` 是**单次 `ParseFile` 的结果**(2146-2147)。多图层要累加多份，但 `Aperture` 里
   **没有"所属图层"字段** → 累加后图层身份丢失。而 `GerberParser` / `Aperture` / `ApertureShape`
   来自外部 `GerberParserTool.dll`（源码不在本工程）→ 要么改那个 dll，要么在本工程用
   "每图层一组 apertures"的外层容器包住。**这是多图层的第一道坎。**
3. `groupBox4`「图层」面板空的 —— UI 位已留好，缺的是数据模型。

### 建议（修正版，待用户拍板）
不合并，做三件小事：① 「加载」→「打开模板」；② Gerber 对话框标题改掉"选择文件"、补状态栏反馈
（`LoadGerberFromPath` **目前完全没有状态栏反馈**，且 `label1` 是 9pt 小字，反馈太弱）；
③ 加"这是模板目录"的拦截提示。三件都不挡多图层的路。
等图层功能做完、输入形态定下来再回头看是否合并 —— 届时答案可能反而是"合并成『打开工程』"。

- 状态重置写了两遍：`LoadGerberFromPath`(794-799) 与 `ExtractPosition`(936-941)

### B. 数据模型裁定（已写入工程根目录 `README.md`）
**废弃"模板"概念，只保留"工程"。** 工程 = 一个目录 = N 个 Gerber 图层 +（可选）circles.json。
`circles.json` 存在 = 恢复选点，不存在 = 空 → "是不是模板"退化为**文件存在性判断**。
（原设计的错误：把"有/无选点"这**状态**当成了**类型**，于是要两个入口、两个加载器、两套保存落点，

- **规则 C**：无法解析的文件**跳过且不进图层容器**，导入后汇总提示一次。判据：`DetectFileType()==false`

  （`GerberParser.cs:244-249`）
- **规则 D**：所有能打开的工程都可编辑（无只读模式）；保存就地写回 `RootPath`
- **circles.json → v2.1**：新增 `TemplateInfo.Layers[]`（FileName + IsVisible，用于恢复勾选状态）与
