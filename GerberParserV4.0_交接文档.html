2026-09-19 修复：「保存后底图消失」与「打开工程后选点不见了」
两个现象各自的根因都在 MainForm.cs，已改动并编译验证（dotnet build， 0 warning / 0 error），共 13 处：
  1. 保存后 Gerber 底图消失 —— 「显示底图」开关在两套绘制路径下口径不一致： DrawGerberMode 无条件画底图（开关在 Gerber 模式下是死按钮，按了画面不动、 状态却已翻转），DrawTemplateMode 才读它。而「保存」会把绘制切到模板模式 → 那个早先按下却没生效的 false 突然生效。修：两处统一判 _showBaseLayer， 并让两个模式的绘制顺序对齐（底图 → 选点 → 限定框）。
  2. 打开工程后选点不见 —— 两处叠加： ① 保存落点条件里带了 _isTemplateMode，而它在「打开工程」时等于"有没有读到 circles.json"， 于是打开一个还没存过选点的目录、编辑完点保存，内容被写到参数设置的模板路径下另起一份； ② 「上次工程」只在「打开工程」时记录，保存不记录 → 下次开机恢复的是旧目录，那里当然没有刚存的选点。 修：就地保存只看"有没有一个真实存在的工程目录"；保存 / 另存成功后把「上次工程」指向实际落点。
  3. 顺带修掉的确定性缺陷：circles.json 只认这一个名字（原来会拿目录里任意 *.json 凑数，读不出 Shapes 还完全静默）；选点对象与图形缓存的匹配加了"退化键"并 回填图层（老 json 没有 Layer 字段，原来打开后选点是"幽灵对象"，点一下就重复、再点取消不掉）； LoadSavedPath 不再把默认保存路径写进 _currentTemplatePath（否则没打开工程时 点保存会在 …\template\template 下套一层）。
接手后请按「六、交互规则速查」逐条实机验证，日志照旧在 exe 目录 logs\ 下。

一、这是什么

一个 Gerber 选点工具的桌面程序。工作流是：

打开 Gerber 底图  →  在图上挑出需要的焊盘 / 针位  →  存成「模板」

模板的产物是一个文件夹，里面是 circles.json（选中的点）+ 一份 Gerber 底图拷贝，供下游设备按模板定位。 使用者的时间几乎全花在"挑点"上，所以这个软件的复杂度集中在选点交互，而不是解析或渲染。

历史沿革（避免看不懂旧注释）：这个工程原来基于 Halcon（HOperatorSet / HWindowControl）， 2026-09-18 已彻底移除 Halcon 依赖，改用自研控件库 Korey.SmartWindow 做 GDI+ 矢量自绘。 代码里大量注释写着"原来用 Halcon 是怎么做的、为什么改"——那是有意保留的，别删。

SelectedCircle 有两个"选中"表达，必须同步

SelectedCircle.IsSelected（对象上的标志，管绘制）与 _selectedCircles（集合成员，管保存） 是两份状态。任何一处改动都要同时改另一处，否则会出现"看起来选中了但保存没写进去"，或者反过来的 "清空之后框选一个都不响应"（IsSelected 残留 true，被当成已选中而跳过）。

历史上就踩过一次：ClearAllSelection() 是为此而生的 —— 它同时复位 _allShapes 上的标志、 清空集合、清掉撤销栈。要清空选择请一律走它，不要直接 _selectedCircles.Clear()。

五、关键设计决策（以及踩过的坑）

这一节是这份文档最该读的部分。每条都是"当时为什么这么定"——不知道这些，很容易改回去。

1. 选点不要门禁

曾经有过一个 _isSelectingMode「选点模式」开关，要先点「锁定」按钮进入，退出后左键点击毫无反应。 用户的第一反应是"软件坏了"。已彻底删除：左键任何时候都能选点，单选 / 多选只是"点一下的语义差异"，不是开关。

教训：不要让用户"先进入某个模式才能操作"，也不要把状态藏起来不给反馈。

2. 框选 = 选择；框选限定 = 作用范围

原始设计里"框选区域"只做一件事：把点击可达范围缩小到框内。它不选中任何东西，而框外点击会静默失效 —— 用户必须先"清除区域"才能去别处点。这是最被诟病的地方。

但直接把区域删掉也不行：它顺带提供了"在区域内按类型批量操作"的能力，而这个能力是真有用的 （比如一片区域里 A、B 要、C 不要 —— 框定范围后点一下 C 就能清掉区域内全部 C）。

最终拆成两件事：

  • 框选 → 框内图形一次性全部选中（累积，只增不减；Ctrl+Z 可撤销）
  • 框选限定 → 最近一次框选留下的矩形，只限定"多选时同类扩散的范围"，不再拦截点击命中

画面上保留一个红框作为限定的指示灯：框在 = 限定生效，框不在 = 作用于全板，两者严格同步。

3. 规则只能有一条：点到框外就解除限定

中途曾实现成"多选会解除限定、单选不解除"（理由是想保留限定方便继续在框内多选）。 结果是同一个动作（点框外）在不同点击方式下行为不同 —— 用户直接当成 bug 报回来。

现在统一由 ReleaseScopeIfOutside() 处理，所有入口（左键单选 / 左键多选 / 右键菜单）共用。 加新交互时也走它，别再写第二份判定。

4. 性能：三处 O(N²) 都在 09-18 修掉了

位置原来的代价现在的做法
每帧重建全部图形每次鼠标点击重建 15,359 个对象，每个还要在已选集合里线性查 → 约 2,960 万次比较 / 次点击_allShapes 构建一次；绘图只画可见范围
每帧算包围盒绘制循环里为每个图形各算一次 → 约 2.36 亿次迭代 / 帧（这就是"一点翻转就卡死"的根因）_contentBounds 缓存
框选时逐个去重去重函数是线性扫描，框 k 个就是 O(k·n)；3,852 点的板全选约 1,480 万次多字段比较（可见卡顿）一次性构建 HashSet（键 (X,Y,Shape)，与缓存索引键一致）→ O(n+m+k)

量级提醒：真实板子上有 1.5 万级图形、模板点 3,852 个。任何"每帧 / 每次点击对全量做循环"的写法都要先算一笔账。

5. 画布背景是纯黑，颜色不能随便挑

kWindowControl1.WindowBackColor = Color.Black。光圈配色表（MainForm.ApertureColors） 已按"对纯黑对比度 ≥ 4.5:1"筛过一遍，剔除了 blue / dim gray / slate blue / dark olive green 四个。

阈值取 4.5:1 而不是非文本图形常用的 3:1，因为光圈是描边绘制的细轮廓（SetDraw("margin")），比色块更难看清。 改配色前先算一遍对比度。

6. GDI+ 的 Color.Green 不是 Halcon 的 green

Halcon 调色板的 green 是纯绿 (0,255,0)，而 GDI+ 的 Color.Green 是 (0,128,0)， 明显发暗。控件库 KWindow.ParseColor 按 Halcon 语义做了覆盖，但 ParamsForm.HalconColorToSystemColor 里曾漏了一处（预览色块比画布暗），已修。

加新的颜色转换时，两头都要按 Halcon 语义对齐。

7. "保存模板"是就地保存，落点必须可见

规则：当前有模板归属就存回它所在目录（不管它在桌面还是哪）；只有"刚从 Gerber 模式新建"时才落到 参数设置里的模板路径。判断依据之一曾经是"文本框里的名字与当前模板文件夹名是否相同"——这个隐式条件让用户完全看不懂存到哪去了。

现在覆盖确认框会显示完整路径，状态栏也显示完整路径。另外「另存到」之后会把模板归属指到新位置 （原来漏了这步，导致另存后再点「保存」写回旧目录）。

2026-09-19 补：判断依据只能看"有没有一个真实存在的工程目录"，不能绕道别的状态位。 当时的写法是 if (_isTemplateMode && _currentTemplatePath 非空)，而 _isTemplateMode 在「打开工程」时被赋成 restoredSelection —— 也就是"那个目录里读没读到 circles.json"。于是打开一个还没存过选点的目录（原始 Gerber 素材目录 正是这种）编辑完点「保存」，程序不写回打开的目录，而是跑到参数设置的模板路径下另起一份。用户以为 存回了打开的工程，下次再打开那里选点是空的。现在条件简化成 !string.IsNullOrEmpty(_currentTemplatePath) && Directory.Exists(_currentTemplatePath)。

配套的一条：保存成功后必须调 RememberLastProject("template", targetFolder)。 原来只有「打开工程」记「上次工程」，所以"打开的是 A、存的是 B"之后，下次开机自动恢复的是 A —— A 里没有刚存的选点，用户看到的就是"选点不见了"。落点在哪，「上次工程」就该指哪。

8. 原子写文件

WriteFileAtomic：先写同目录 .tmp，再 File.Replace 替换。 原实现在 File.Delete 与 File.WriteAllText 之间有危险窗口 —— 崩在中间会让模板只剩 Gerber 而 JSON 已丢， 原数据不可恢复。改文件写入时别退回直接 WriteAllText。

9. 浮层工具栏的"视口让位"是控件库能力，不要自己算

AttachOverlayToolbar(toolbar, ToolbarEdge.Top) 会自动同步 ViewPadding， 让 FitToWindow 把内容居中到"工具栏没占的那块"——工具栏只压留白、不压图。 手动调 padding 反而会打架。

另：工具栏按钮是运行时按需生成的，设计器无法序列化，所以它刻意留在代码里（BuildOverlayToolbar()）， 不在 Designer.cs 里。

「显示底图」开关

真值只有一个字段 _showBaseLayer，三个入口（画布悬浮工具栏的 toggle、菜单「视图 → 显示底图」、 画布右键菜单）全部走 SetShowBaseLayer()，靠 _syncingBaseLayer 挡回环。

绘制路径是否读这个开关
DrawGerberMode（Gerber 模式）读（2026-09-19 起）
DrawTemplateMode（模板模式）读
这两行必须永远保持一致。曾经 DrawGerberMode 是无条件画底图的 —— 那让这个开关在 Gerber 模式下变成死按钮：按下去画面不动、状态栏也不动，用户以为按钮坏了； 但状态已经翻转成 false，等到某个动作把绘制切到模板模式（点一次「保存」就会）， 那个迟到的 false 突然生效 —— 表现为"保存后 Gerber 底图消失"。 一个开关只允许有一套口径：不显示就是不显示，现在按下当场生效，并有状态栏回执。

另外两个绘制路径的顺序也必须一致：底图 → 选点 → 框选限定框（先画的在下层）。 模板模式原来把底图放在最后画，等于把光圈描边叠在已选点上层，于是"保存前 / 保存后"观感不同 —— 绘制内容不该因为存了一次盘而变样。

同步 toggle 时一定要防递归

工具栏的 toggle 与界面上的 RadioButton 共享同一份状态，互相赋值会触发对方的 CheckedChanged， 形成"点 A 设 B、B 的回调又把 A 设回来"的回环。SetClickMode / 底图开关都用 _syncingClickMode / _syncingBaseLayer 标志包住 —— 加新的双向同步时照做。

七、雷区（容易踩，别踩）

1. bin\x64\Debug\Json\ 是使用者的模板数据

不可再生。清理 bin、重编、改输出路径之前都要确认它安全。

2. 不可还原的依赖必须放 lib\（2026-09-19 已修）

GerberParserTool.dll（28,672 B）原来从 bin\Debug\ 引用，而 bin/ 已在 .gitignore 里 —— 后果是克隆仓库后直接编译不过，且清空 bin 后同样编不过。 现已挪到 lib\ 并改 HintPath，与 Korey.SmartWindow.WinForms.dll 同一做法。

判据就一条：能不能由 NuGet 还原？ 能 → 走 packages/ 并忽略； 不能 → 放 lib\ 并进版本库。 （GerberParserTool 的 pdb 刻意不带来：调试符号里嵌着源码机器的绝对路径， 对使用方无用，还会泄露目录布局 —— dll 本身不需要它。）

3. Program.FileName 仍是隐式全局状态

跨类使用的静态字段（MainForm 之外也有引用），这一条坑还在： 任何一处悄悄改了它，别的读取点都会受影响。真正的状态源应该是 _currentTemplatePath（工程归属）。

默认值那一条已修（2026-09-19）：原来是原开发者本机的一个绝对路径 （形如 C:/Users/<用户名>/Desktop/<工程>/Gerber/<文件>.GBS）， 换机必然失效，而且这个字符串会进版本库、把本机用户名公开出去。现在默认值是 string.Empty —— 下游的读取点本来就是按 string.IsNullOrEmpty 判状态的， 空串是它们的预期取值，不是缺值。

同一轮还删掉了 MainForm.GetGerberBrowseStartPath() 里那条硬编码兜底目录 （同样是本机路径），现在退到 Environment.SpecialFolder.DesktopDirectory。

4. 本工程源码是 UTF-8 带 BOM + CRLF

批量改文件时务必保持。用脚本改的话：读进来之后按首 3 字节判断 BOM 再写回， 换行统一成 CRLF。把它改成 LF 会让整个文件的 diff 爆炸。

5. 沙盒里其实能编译 —— 用 dotnet build，绕开 MSBuild.exe

MSBuild.exe 会被某些受限环境判定为受限二进制（LOLBin）拦下，但 dotnet build GerberParserSmartV4.0.csproj -c Debug -p:Platform=x64 走的是托管版 MSBuild（MSBuild.dll），完全可用。2026-09-19 实测：本工程（老式非 SDK 风格 csproj + packages.config）约 2 秒，0 warning / 0 error。前提是本机有 v4.8 targeting pack （C:\Program Files (x86)\Reference Assemblies\Microsoft\Framework\.NETFramework\v4.8）。 所以"改完能不能编"本身是可以先验证的，别把它整个推给接手的人。

注意 -c Debug 不带 -p:Platform 时走 Debug|AnyCPU → 输出到 bin\Debug\；要复现真实运行配置请显式加 -p:Platform=x64。 另外想完全不碰既有输出目录，可以加 -p:OutputPath=<临时目录>\（全局属性会覆盖 csproj 里的赋值）。

6. _isTemplateMode 不是"有没有打开工程"

它现在的实际含义只是绘制选点的口径（模板模式画全部模板点 / Gerber 模式只画已选中的）， 而且在「打开工程」时等于 restoredSelection（那个目录里有没有读到 circles.json）。 把"工程是否已打开"或"保存该往哪写"挂在它上面，就会得到"打开一个没有选点的目录 → 保存跑到别处"这种结果 （见第五节第 7 条的 09-19 补记）。要判断工程归属，只看 _currentTemplatePath 有没有指向一个真实存在的目录。

7. 选点对象必须是图形缓存里的同一个实例

_selectedCircles 里的 SelectedCircle 与 _allShapes 里的必须是同一批对象。 原因很硬：HandleSingleSelect 用 List.Remove(clicked) 取消选中，比较的是引用； 一旦是两份实例，就表现为"点一下能选中、再点一下取消不掉"，而且同一位置会被画两遍。

保证它的机制在 BuildAllShapes()：用两级索引（①图层+坐标+形状 与 ②坐标+形状）去复用已选点对象。② 是为了兜住 v2.2 以前没有 Layer 字段的 circles.json —— 那种文件恢复出来的选点 Layer 全是空串，只靠 ① 永远匹配不上。 命中 ② 时会顺手把真实图层回填进选点；保存端从 v2.2 起写 Layer，闭环。

坐标比对用 Math.Round(…, 4)：保存端就是这个精度，两边做同一次舍入 → 精确相等，不需要容差。 改坐标精度时两处必须一起改，否则又会对不上号。
