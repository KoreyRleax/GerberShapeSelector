# 沙盒环境与工具链

- **首次记录**：2026-09-19（接手时），2026-09-21 补充
- **状态**：（已确认）环境限制与应对办法，非代码问题
- **关联**：`.workbuddy/memory/MEMORY.md`「二、环境与工程约定」

> ⚠ **本工程与桌面 RBLAOI 相反**：RBLAOI 里 `MSBuild.exe` 被拦且 `dotnet build` 跑不通 WPF，
> 所以那边"编译只能靠用户本地"；**本工程是 WinForms + 老式 csproj，`dotnet build` 完全可用**，
> AI 侧可以自己编译验证。不要把 RBLAOI 的结论套过来。

## 一、现象

AI 会话在本机沙盒里干活时会撞到三类情况：**命令被拦**（编译 / cmd）、**文件被意外改写**（行尾变 LF）、
**看不到输出**（stdout 不回传）。它们不报错、不崩溃，但会让"改完自验"这一步失真。

## 二、影响

- 不知道这些限制，会把"沙盒拦下的命令"误判成"工程编不过"，或把"Edit 改了行尾"当成代码问题。
- 反过来，**本工程能编译**这一点必须记住 —— 否则会像 RBLAOI 那样把编译验证整个推给用户，
  白白拉长一轮返工。

## 三、根因

**① 沙盒安全策略**（与工程无关）：
`MSBuild.exe` 被判为 LOLBin（"可执行任意代码的合法二进制"）；
`cmd.exe` 禁止从 PowerShell 工具调用；`Add-Type` 被拦（运行时编译并加载 .NET 代码）；
Bash 工具的运行环境 PATH 异常（`ls` / `grep` / `dirname` 全部 `command not found`，exit 127）。

**② 工具实现细节**（不是安全策略）：
Edit 工具可能把**整个文件**重写成 LF（本工程要求 UTF-8 BOM + CRLF）；
PowerShell 工具的 stdout 回传不稳定（有时只回最后一段）。

## 四、解决方案

### 4.1 能做的事（实测）

| 能力 | 命令 / 做法 | 实测 |
|---|---|---|
| **编译自验** | `dotnet build GerberParserSmartV4.0.csproj -c Debug -p:Platform=x64 -p:OutputPath=<仓库外目录>` | **1.6 ~ 8.4 s，0 warning / 0 error** |
| 规避污染 | 上面那条把 `OutputPath` 指到仓库外（如 `C:\Users\59538\.workbuddy\tmp\`） | **不会碰 `bin\x64\Debug\Json\`**（那是使用者的模板数据，不可再生） |
| 读日志 | 日志在 exe 目录 `logs\yyyy-MM-dd.log` | 排查首选，比猜快 |
| 中文输出 | `[Console]::OutputEncoding=[Text.Encoding]::UTF8` + `$env:DOTNET_CLI_UI_LANGUAGE='en'` | 否则乱码 |

`dotnet build` 走的是**托管版 MSBuild**（`MSBuild.dll`），与"`MSBuild.exe` 被判为 LOLBin 拦下"
是两回事。前提：本机有 v4.8 targeting pack（`C:\Program Files (x86)\Reference Assemblies\Microsoft\Framework\.NETFramework\v4.8`）。

### 4.2 不能做的事 → 绕行办法

| 限制 | 表现 | 应对 |
|---|---|---|
| `MSBuild.exe` 直接调用 | `Command blocked for security: Known LOLBin …` | 用 `dotnet build`（见上） |
| `cmd.exe` | `cmd.exe cannot be used from the PowerShell tool` | 用 PowerShell 本身 |
| **Bash 工具的 PATH 损坏** | `ls` / `grep` / `dirname` / `tail` 一律 `command not found`（exit 127） | 用 Glob / Grep / Read 工具代替 |
| `Add-Type` | 被拦（"compiles and loads .NET code at runtime"） | 不能靠它加载自定义 .NET 代码 / P/Invoke |
| WPF 工程的 `dotnet build` | 不执行 XAML 编译阶段，GAC 引用解析不到 | 本工程是 WinForms，不受影响；若将来转 WPF 需另想办法 |

### 4.3 工具本身的坑（**改完文件后必看**）

### 3.1 Edit 工具可能把整个文件写成 LF

本工程源码是 **UTF-8 带 BOM + CRLF**（`git config core.autocrlf=true` → 工作区应为 CRLF）。
但 Edit 工具**有时会把整个文件重写成 LF**：

- 2026-09-21 实测：`ShapeQuery.cs` 中招（216 行全 LF），**同一批改的 `MainForm.cs` 却没事**。
- 判断依据：`git ls-files --eol <file>` 看 `w/` 字段是否 `crlf`。
- 修法（PowerShell）：

  ```powershell
  $t = [IO.File]::ReadAllText($p)
  $t = $t -replace "`r`n","`n"
  $t = $t -replace "`n","`r`n"
  [IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))
  ```

→ **每次改完 .cs 都要复验行尾**，不能想当然（"上次没事"不代表这次没事）。

### 3.2 PowerShell 工具的 stdout 不可靠

实测：有时回传、有时只回传最后一段。**稳妥做法是 `Out-File` 落盘，再用 Read 工具读**。
本目录里多数脚本示例都遵循这个模式。

### 3.3 同一文件的多处 Edit 不能并行

并行下发时后写覆盖前写（实测 4 处修改只落盘 2 处）。**必须串行**。

### 3.4 替换"方法签名行"时要把它的 `{` 一起取

只取签名行、新内容又写了 `{` → 花括号多一个（编译必错）。

## 五、绝对不要碰的东西

| 路径 | 为什么 |
|---|---|
| `bin\x64\Debug\Json\` | **真实使用者的模板数据，不可再生**。清理 `bin` / 重编 / 改输出路径前必须确认它安全 |
| `.git\refs\**` 的写操作 | 沙盒拦写却返回成功，会**静默删掉分支引用** —— 提交/推送一律由用户在本机终端做 |

## 六、遗留

- 上面的限制都是沙盒侧策略，与工程本身无关。若环境放行 `MSBuild.exe`，第一条记录可标（已失效）。
- 临时产物一律写到仓库外（`C:\Users\59538\.workbuddy\tmp\`），**不要**在工程目录里留
  `_xxx.py` / `_xxx.txt` 之类一次性文件 —— 用户 `git add -A` 会把它们一起提交。
