# 选点只能选到最大圆圈那一层

- **首次记录**：2026-09-21
- **状态**：✅ 已完成（2026-09-21，**分两轮**）
  - 第一轮：分层命中（先叠放、同层再比距离）—— 用户实机回归确认生效；
  - 第二轮：**同层内**的排序键（原来缺这一档，表现为"只有一个图层也总是选最大那个圆"）——
    见 §5.4，已用脚本对照验证。
- **关联**：`MD文件汇总（AI）/任务&需求/R-20260921-01-多图层选点与图层顺序.md`；
  `MD文件汇总（AI）/待办/待办清单.md` T20 / T22

## 一、现象

> **用户原话（第一轮）**：
> "多图层下，选点只能选最大圆圈的图层，应该是仅最上面的图层允许被选点。"

> **用户原话（第二轮，第一版修复之后）**：
> "图层仍然只能选择最大圆圈的。"

复现条件：**多图层工程**（实测 6 层：`top.o` / `smt.o` / `smb.o` / `past-b.o` / `drl.o` / `bot.o`），
在同一坐标有多个图层图形的地方点击 —— 不论点在哪、点哪个位置，
选中的**永远是同一个图层**（那个含最大圆圈的层）。

一个典型位置（用户回归日志）：光标附近同时压着 **5 个图形**，分属 5 个图层。

## 二、影响

- 这个程序的全部价值就是"在叠加图层上挑点"。选不中想要的那一层 = **功能不可用**。
- 因为"只能选到一层"，用户无法给别的图层选点，模板数据会整体偏掉。
- 严重度：**阻断级**。

## 三、定位过程

1. **读命中实现**：`ShapeQuery.HitTest` 的取值逻辑是"返回离点击位置**最近**、且距离不超过容差的图形"，
   距离用 `DistanceToBoundary`。
2. **算一遍圆内部的边界距离**：`d = len − r`（`len` = 点到圆心距离，`r` = 半径）。
   在同一个点上，`len` 相同，**`r` 越大 `d` 越小**。
3. **代入用户的真实量级**（同一点，`len = 0.30`）：

   | 图形 | 半径 r | 边界距离 `len − r` | 谁赢 |
   |---|---|---|---|
   | 上层的小焊盘 | 0.25 | **+0.05** | |
   | 下层的大焊盘 | 1.50 | **−1.20** | ← 永远赢 |

   → 这不是"偶尔选错"，而是**系统性偏向大图形**，与用户的描述完全吻合。

4. **第一版修复后用户仍报"没生效"** → 复查第一版的实现，发现它靠
   `shape.Layer`（字符串）去 `layer.FileName` 匹配出的字典里查深度。这类匹配一旦对不上，
   `GetShapeLayerDepth` 对所有图形都返回 `-1`（**全都相同**）→ 命中**静默退回纯距离排序**
   → 又回到"大圆通吃"，而且没有任何报错。

## 四、根因

**根因 A（第一层）：命中的排序键用错了维度。**

`HitTest` 只比"点到边界的距离"，它表达的是**几何接近度**，而不是"用户看到的是谁"。
多图层叠加下这两件事不是一回事 —— 用户看到的是**画在最上层**的那个图形。

**根因 B（第二层，第一版修复失败的真正原因）：图层状态用"图层名字符串"关联，会静默失败。**

只要有一处对不上（老数据、命名差异、以后改命名规则），查询就整体失败，
表现为"代码明明改了，行为却没变"，且**无任何报错可查**。这是比根因 A 更危险的一类缺陷：
它把"改错了"伪装成"没改"。

## 五、解决方案

### 5.1 命中改成两级比较（先叠放，后距离）

```csharp
// ShapeQuery.HitTest(...) 的核心比较（两句注释原文保留在代码里）
int depth = layerDepth == null ? 0 : layerDepth(s);
if (depth == SkipDepth) continue;              // 图层被隐藏等：本次不参与命中

double d = DistanceToBoundary(s, x, y);
if (d > toleranceWorld) continue;

// ⚠ 先比叠放（值大者胜），同层再比距离（近者胜）——
//    这一句的先后次序就是整个修复的要害，调换回去就等于退回"大圆通吃"。
if (best == null || depth > bestDepth || (depth == bestDepth && d < bestDistance))
```

- 代码位置：`ShapeQuery.cs:97`（`SkipDepth` 常量）、`ShapeQuery.cs:123`（`HitTest` 签名与循环）
- 图层知识留在 `MainForm`（`DepthForHitTest`，`MainForm.cs:2895`），
  `ShapeQuery` 保持**无状态几何库** —— 改判定口径只改 `ShapeQuery`，改"哪层算上层"只改 `MainForm`。
- **最上层在该处没有图形时穿透到下一层**（不是"仅最上层可点"）。

### 5.2 图层状态直接拷进图形（消灭字符串匹配）

- `SelectedCircle` 加三个**运行期**字段（不进 `circles.json`）：`LayerId` / `LayerDepth` / `LayerHidden`
  （`MainForm.cs:128` 附近，用**属性初始化器** —— 本类 4 个构造函数里 3 个没有 `: this()` 链到无参构造，
  写在无参构造里必漏）
- `LayerInfo` 加 `Id`（会话内唯一、置顶重排不变）与 `ColorIndex`（配色，同样不随重排变）
- `BuildAllShapes`（`MainForm.cs:2308`）建 `Dictionary<Aperture, LayerInfo>` ——
  **用对象引用做键**：`_layers[li].Apertures` 里的那些 Aperture 对象就是这一层的，引用相等，骗不了人
- `RefreshLayerState()`（`MainForm.cs:2841`）把深度 / 隐藏状态刷进每个图形；
  调用点三处：`RefreshLayerPanel()` 的早退**之前**、`OnLayerRowVisibilityChanged()`、`MoveLayerToTop()`
- `DepthForHitTest`（`MainForm.cs:2895`）变成纯字段读取：
  `shape.LayerHidden ? SkipDepth : shape.LayerDepth`

### 5.3 加了诊断日志（排查完可删）

- `LogHitDiagnostics`（`MainForm.cs:2968`）：每次选点写一行"光标附近图形的图层与深度（按深度降序）+ 实际命中者"。
  **命中者必须是列表第一个**；所有深度都一样就说明归属没接上；还会报"图层总数"（=1 时特别标注）。
- `LogLayerOrder`（`MainForm.cs:2942`）：载入工程 / 置顶后写一行"图层叠放顺序（从最上层到最下层）"。

用户的第一份回归日志正是靠它确认了修复生效：

```
09:32:51  附近 5 个图形 [top.o#5 | smt.o#4 | smb.o#3 | drl.o#1 | bot.o#0(隐)]；→ 命中 top.o#5
09:32:56  附近 5 个图形 [drl.o#5 | smt.o#4 | top.o#3 | smb.o#2 | bot.o#0(隐)]；→ 命中 drl.o#5
```

### 5.4 补上"同层内"的排序键（2026-09-21 第二轮）

第一轮修完后，用户报**只有一个图层**时仍然"总是选中最大那个圆圈"。

- **为什么分层优先救不了它**：只有一个图层时 `layerDepth` 全体相同，第一档直接失效，
  最终只剩"边界距离"这一档 —— 而圆内部的 `d = len − r`，半径越大越负，**大圆必然通吃**。
  所以这不是"没修干净"，是**同层内压根没有正确的排序键**。
- **修法**：比较键从两级扩到四级 ——

  | # | 键 | 方向 |
  |---|---|---|
  | ① | 图层叠放 `layerDepth` | 大者胜（用户看到的是最上层） |
  | ② | 是否**命中内部**（`d ≤ 0`） | 命中内部 > 只是落在容差里 |
  | ③ | 都在内部 → **尺寸**（`AreaProxy` = 半宽×半高） | **小者胜**（用户点的是那个"具体"的图形） |
  | ④ | 都在容差内未命中内部 | 边界距离近者胜（原口径） |

- 代码位置：`ShapeQuery.cs` 的 `HitTest` 循环 + 新增 `AreaProxy`。
- **脚本对照验证**（照搬新旧两套规则跑典型场景，容差 4 世界单位）：

  | 场景 | 旧 | 新 |
  |---|---|---|
  | 同心大小圆（r=10 / r=1），点在 r=0.3 处 | r=10 ❌ | **r=1** ✓ |
  | 错开大小圆，点落在小圆里 | r=10 ❌ | **r=1** ✓ |
  | 只在大圆内（小圆够不着） | r=10 | r=10（不变） |
  | 上层该处无图形 → 穿透 | r=10 | r=10（不变） |
  | 空白处，容差内边界最近 | r=2 | r=2（不变） |

  → **只在"命中多个图形内部"时结论改变**，其余场景行为一字未动。

### 5.5 🔴 图层身份"分配晚了半拍"——置顶失灵的真凶（2026-09-21 第三轮）

**用户原话**：
> "我之前不是让你改为，置顶图层优先吗，我把小圆图层置顶了，为什么选的是大圆图层？"
> "原本是没有的，你改动之后就有这个 bug"

**根因**：`FinishProjectLoad` 的调用顺序把因果颠倒了。

```
BuildAllShapes();      // ① 把 owner.Id 写进每个图形当身份（LayerId）
                       //    但此刻 LayerInfo.Id 还是初值 0 —— 于是 LayerId 全被写成 0
...
RefreshLayerPanel();   // ② 内部才 RefreshLayerState() → 这时才分配 Id = 1,2,3…
```

`RefreshLayerState` 的拷贝逻辑是 `if (s.LayerId > 0 && …)`，`LayerId = 0` 全部落进 else 分支：

```csharp
s.LayerDepth = -1;      // ← 全体 -1 = 全体深度相同
```

→ `HitTest` 的第①档"叠放优先"**静默失效** → 置顶哪个图层都不起作用。

**为什么它藏了这么久**（用户说"原本没有"是对的）：

| 路径 | 结果 |
|---|---|
| 打开**存过选点**的工程 | `LoadProjectFromFolder` 之后会**恢复选点** → 再跑一次 `BuildAllShapes`，那时 Id 已分配 → **侥幸正常** |
| 新建工程（无选点可恢复） | **没有**第二次 `BuildAllShapes` → **必然中招** |

2026-09-21 新增的"新建工程载入完自动保存"流程，恰好让用户第一次认真走新建路径 —— 于是把它引爆了。
**它不是新引入的 bug，是一条既有的顺序缺陷被新路径暴露。**

**修法**：把"分配图层 Id"从 `RefreshLayerState` 里抽成 `EnsureLayerIdentity(depthOf)`，
并在 **`BuildAllShapes()` 之前**显式调用（`FinishProjectLoad` 与 `AppendLayersFromFiles` 两处）。

**顺带加了一条自检**（`BuildAllShapes` 末尾的构建日志）：

> `⚠ 有 N 个图形没有图层身份（叠放优先级对它们失效，置顶将不起作用）`

`LayerId <= 0` 的图形数正常应为 0。非 0 就是这类问题的**直接指纹** ——
这类缺陷的危害不在于报错，而在于**改错了却看不出任何异常**，所以必须给它一个能自证的信号。

**教训**：写入方（`BuildAllShapes` 写 `LayerId`）依赖的前置条件（Id 已分配），
不能靠"另一个方法碰巧在我之前跑过"来满足。**跨方法的隐式顺序依赖，要么抽成显式的第一步，要么写进断言。**

## 六、优劣 / 备选方案

| 方案 | 结论 |
|---|---|
| **先比图层叠放，同层再比距离**（采用） | 与"用户看到的是最上层"一致；同层内仍按"离光标最近"取胜，单图层行为完全不变（`layerDepth == null` 时退化为旧口径） |
| **仅最上层可点（严格不穿透）** | **否**。下层整层点不动 —— 用户想选的点恰好在最上层没图形的位置时界面毫无反应，这正是本工程历史上最被诟病的问题（"点了没反应，以为软件坏了"）。2026-09-21 与用户确认，选**穿透** |
| **只比距离但按图层加权**（距离 × 图层系数） | **否**。权重调不出稳定手感，且"多大系数算合理"无法解释 |
| **给 HitTest 传"可见图层集合"** | **否**。与"深度优先"是两件事，一个委托表达得更清楚 |
| **把图层状态放在 MainForm 的字典里现查**（第一版） | **否**。要求字符串逐字符相等，失败时静默退化 —— 已付出一次返工代价 |
| **用 `LayerInfo` 对象引用做图形的归属**（采用） | 不会失败；且顺带让"隐藏过滤"与"命中优先级"共用同一份数据 |
| **给图形存 `Layer` 字符串并在变化时重建字典** | **否**。仍然依赖字符串，理由同上 |

**代价**：图层顺序或显隐变化时要跑一次 O(图形数) 的刷新（1.5 万图形 ≈ 1 ms，
相当于用户点一次复选框的代价，可接受）。
