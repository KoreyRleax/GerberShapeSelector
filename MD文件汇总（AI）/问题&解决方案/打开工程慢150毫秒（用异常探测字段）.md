# 打开工程慢 150 毫秒（用异常探测字段）

- **首次记录**：2026-09-21
- **状态**：（已完成 2026-09-21）AI 侧编译验证通过；待用户复测耗时
- **关联**：`MD文件汇总（AI）/任务&需求/R-20260921-01-多图层选点与图层顺序.md`；
  `MD文件汇总（AI）/待办/待办清单.md` T26 / T09

## 一、现象

> **用户原话**：
> "另外我发现，采样清晰度加载又好像变慢了，我也不确定。"（随后确认这句是误发，不必处理）

但顺着这句去量日志时，**发现了一处真实的开销**：从"打开工程"到"视图已重置"的耗时里，
有一段 150 ms 的空档没有任何理由。

```
09:32:09.525  加载模板: q02578f044a00
09:32:09.530  打开工程：从 circles.json 恢复 2 个选点
09:32:09.680  打开工程：已恢复 6 个图层的勾选状态与图层顺序   ← 中间 150 ms
09:32:09.692  图形缓存构建完成：20188 个图形（12 ms）
```

中间只做了一件事：`ApplyLayerVisibility` 里 **6 个图层的循环**。6 次循环花 150 ms 是不合理的
（同一次日志里，**建 20188 个图形的缓存只花 12 ms**）。

## 二、影响

- 单次 150 ms 人眼几乎察觉不到，但它**每次打开工程 / 每次自动恢复上次工程都要付**。
- 性质上更值得记的是**成因**：用异常做"字段存在性探测"，属于那种"看不见的成本"。

## 三、定位过程

1. 从日志时间戳切出各阶段耗时（**日志本身就是测点**，无需额外插桩）：

   | 阶段 | 耗时 |
   |---|---|
   | 解析 6 个 Gerber 文件 | 410 ms |
   | 建 20188 个图形的缓存 + 图层状态刷新 | **12 ms** |
   | 读 circles.json + 恢复选点 | 5 ms |
   | **恢复图层勾选状态** | **150 ms ← 异常** |
   | 重建缓存（带选点） | 12 ms |

2. 读 `ApplyLayerVisibility` 的实现，看到这一段（2026-09-21 第二轮我写的）：

   ```csharp
   // v2.3 起才有 ColorIndex；老文件读不到就保持 -1，稍后按当前顺序分配。
   try { layer.ColorIndex = (int)item.ColorIndex; }
   catch { layer.ColorIndex = -1; }
   ```

3. **老工程的 json 里没有 `ColorIndex`** → `item.ColorIndex`（`dynamic` 点属性）抛
   `RuntimeBinderException` → **每个图层抛一次** → 6 次异常 = 150 ms。

## 四、根因

**用异常来控制流程。**

用 Newtonsoft 的 `dynamic`（实际是 `JObject`）**点属性**访问一个不存在的字段，
不是返回 null，而是**抛 `RuntimeBinderException`**。
异常的代价包括：构造异常对象、抓调用栈、DLR 绑定失败、栈展开 ——
单次量级在**毫秒到十几毫秒**，放在循环里就变成"每次打开工程白花 150 ms"。

正确做法：**Newtonsoft 的 `JToken` 索引器 `item["Field"]` 取不到字段时返回 `null`**，
根本没有异常 —— 这就是为"字段可能不存在"准备的接口。

## 五、解决方案

`ApplyLayerVisibility`（`MainForm.cs:3303`）整体改用 `JToken` 索引器：

```csharp
JToken root = jsonData as JToken;
if (root == null) return;

JToken tinfo = root["TemplateInfo"];
JArray layers = tinfo == null ? null : tinfo["Layers"] as JArray;
if (layers == null) return;

foreach (JToken item in layers)
{
    string fileName = (string)item["FileName"];
    ...
    JToken vis = item["IsVisible"];
    layer.IsVisible = (vis == null || vis.Type != JTokenType.Boolean) || vis.Value<bool>();

    // v2.3 起才写 ColorIndex；老文件取到 null 就保持 -1，稍后按当前顺序现分配。
    JToken ci = item["ColorIndex"];
    layer.ColorIndex = (ci != null && ci.Type == JTokenType.Integer) ? ci.Value<int>() : -1;
    ...
}
```

需要 `using Newtonsoft.Json.Linq;`。方法签名仍是 `dynamic`（调用方传的就是 `JObject`，
`as JToken` 成功），改动面最小。

**预期效果**：那条路径从 ~200 ms 降到 ~50 ms 以内（150 ms 的异常开销归零）。

## 六、优劣 / 备选方案

| 方案 | 结论 |
|---|---|
| **`JToken` 索引器**（采用） | 天然返回 null，零异常；顺带把 `IsVisible` 也做了类型检查（原来是 `(bool)item.IsVisible`，类型不符一样抛） |
| `try/catch` 探测字段（原实现） | **否**。功能上"能用"，代价是每次遇到缺失字段都付一次异常 |
| 先反序列化成强类型类再读 | 更好，但改动面大（整个读取路径都要动）；已列为技术债 T09 |
| 用 `((JObject)item).ContainsKey("ColorIndex")` | 也可以用，但索引器 + 类型判断一步到位，代码更短 |

**通用教训**（已写进 `.workbuddy/memory/MEMORY.md`）：
> 不要用 `try/catch` 探测 JSON 字段在不在。`JToken` 索引器取不到就是 null。

## 七、遗留

- **`LoadJsonFormat` 仍然用 `dynamic` 点属性读选点**（`Shapes.Circles` / `Rectangles` / `Ovals`
  及其字段）—— 缺字段会抛异常，被外层 catch 捕获后整个工程会被判成"选点文件读取失败"，
  用户只看到一句提示、选点全空。建议同批改成 `JToken` 索引器。
  见 `MD文件汇总（AI）/待办/待办清单.md` **T09**。
- 本条只修了"图层清单"这一处；**读选点那条路径的耗时**没有实测过（日志里它只占 5 ms，
  因为当前 json 字段完整）。
